# Issue #1: pre-entry `nnrtld` crash on real hardware

Источник: [GitHub Issue #1](https://github.com/Vlan3ik/repentance-plus-switch/issues/1).
Это разбор отчёта о падении сразу после запуска игры на физической консоли,
а не утверждение о найденной первопричине.

## Краткий вывод

Падение происходит в загрузчике до входа в `main` игры; `Repentance.nro` не
зафиксирован как загруженный успешно. Поэтому Lua/API/game-RVA код не успевает
выполниться и его runtime-поведение не является причиной этого конкретного
падения. При этом
изменения встраивания или линковки могут менять layout самого NSO и остаются в
области проверки loader crash.
Наличие совпадающих статических хешей релизного NSO подтверждает соответствие
артефакта сборки, но не доказывает его работоспособность на железе.

## Подтверждённые факты

- В отчёте консоли: `Result 0x4A8` (Data Abort), `FAR = 0`.
- `PC = nnrtld + 0xA24`, `LR = nnrtld + 0x570`.
- В трассировке присутствует только loader thread.
- Module ID exlaunch для v0.2: `BA4DB187415F043117D6F7D90674AF39D45BBC93`.
  Он в точности совпадает с commit `48dafa3`, помеченным как `v0.2.0-alpha`.
- `subsdk9`, извлечённый из опубликованного GitHub ZIP-релиза `v0.2.0-alpha`,
  имеет SHA-256
  `b448277bd53d68f6c9dd6832c884e2a65eed3b8722ebedcdfa7442e42f4f901`
  и размер `914795` байт.
- Сегментные хеши NSO из релиза проходят статическую проверку.
- Целевой `main` имеет Build ID
  `B6E5BDB9DC12E1D1A25CBFDA17F4BE24B4754EF5`; он совпадает с Build ID в
  crash report.
- Build ID `Repentance.nro` в crash report отсутствует: этот NRO не записан как
  успешно загруженный; по report нельзя исключить неуспешную попытку его
  загрузки.
- Crash report не позволяет подтвердить содержимое каталога на SD: наличие или
  отсутствие `main.npdm`, второго `subsdk9` либо других конфликтующих файлов
  остаётся неизвестным до проверки пользователем.

## Интерпретация и границы вывода

`nnrtld` — ранний runtime link-editor: он выполняется первым и подготавливает
загруженные NSO до передачи управления приложению. `PC` в `nnrtld` вместе с
`FAR = 0` совместим с обращением к нулевому адресу на раннем этапе загрузки.
Это объясняет класс сбоя, но по этим данным нельзя установить, какая именно
структура, релокация, адрес или входной файл вызвал обращение.

Следовательно, подтверждено только **до-entry loader crash**. Следующие
объяснения остаются гипотезами и не должны считаться диагнозом:

- malformed или несовместимые `MOD0`/`.dynamic`, relocation tables или segment
  layout в заменённом NSO;
- несовместимое содержимое одного из заменённых NSO или его метаданных;
- ошибка в порядке/составе exefs или в применении override;
- различие версии Atmosphère/Horizon между тестовой консолью и средой сборки;
- реальная аппаратная/адресная особенность, которую не воспроизводит
  эмулятор.

Текущие исходники и текущий output проекта отличаются от v0.2 и поэтому сами
по себе не доказаны ни как причина, ни как исправление этого сбоя.

## Чек-лист переустановки для пользователя

1. Сохранить crash report и debug log до удаления старого содержимого.
2. Удалить только `sd:/atmosphere/contents/010021C000B6A000/` либо убрать из
   него старые файлы этого проекта, не смешивая их с другим `subsdk9`.
3. Распаковать один выбранный релиз заново, сохранив структуру
   `exefs/subsdk9` и `romfs/` без переименований.
4. Проверить SHA-256 и размер `subsdk9` по таблице релиза; не добавлять
   `main.npdm`, `main`, `subsdk0..8` или `sdk` из постороннего пакета.
5. Убедиться, что версия игры и Build ID `main` равны указанным в релизе, затем
   выполнить полный перезапуск игры и Atmosphère.
6. Если сбой повторяется, не менять одновременно несколько файлов: приложить
   новый report и точный список содержимого каталога title.

## Какие данные нужны для следующего сравнения

- полный неизменённый crash report (`.log`), включая module list и thread
  context;
- версии Atmosphère, Hekate/загрузчика и firmware, тип sysMMC/emummc;
- список файлов
  `sd:/atmosphere/contents/010021C000B6A000/` с размерами и SHA-256;
- точный релиз/commit проекта и дата установки;
- debug log Atmosphère со строками loader и `[isaac-port]`, если такие строки
  доступны (на pre-entry падении их может не быть);
- если возможно, повторный report после запуска на чистом title-каталоге без
  других exefs override.

## Следующие инженерные шаги

1. Воспроизвести запуск с минимальным набором: только релизный `subsdk9`, без
   дополнительных exefs override, и записать loader log.
2. Сопоставить порядок и состав NSO, которые реально видит loader, с
   ожидаемым exefs; отдельно подтвердить отсутствие `.stub` и старых файлов.
3. Проверить тот же артефакт на совпадающей версии Atmosphère/Horizon и
   сравнить module list/адреса до входа в `main`.
4. Если минимальный набор всё ещё падает, получить отладочную трассу
   `nnrtld`/loader или бинарную выборку, достаточную для анализа инструкций
   `nnrtld+0xA24` и цепочки возврата. Только после этого выбирать точечное
   исправление.
5. После устранения pre-entry crash отдельно возвращаться к успешной загрузке
   `Repentance.nro`, Lua bootstrap и API coverage; это другой этап диагностики.
